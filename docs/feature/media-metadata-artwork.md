# 媒体资料与图片功能方案

状态：debug 搜索卡片已接入图片试验，尚未接入来源删除流程，也未完成产品验收。本文集中维护频道和影视资料、图片匹配、本地保存与删除；页面布局由使用本能力的页面 Spec 维护。

2026-11-27 实施范围：用户要求尝试实现并运行单测，在指定设备运行项目；电影接口先提供本机可配置入口，不提供或提交 Key，优先验证无需 Key 的频道与电视剧图片。当前首页由另一会话开发，本轮不改动其页面与交互；图片展示和删除入口未确定，不能把底层能力通过等同于页面功能完成。数据源的产品分发、署名和持久保存授权仍需确认，先作为技术验证，不默认对最终用户启用。

## 目标与范围

用户希望 PlayTV 按确定规则为直播频道、电影和电视剧获取小图与大背景图：首次获取后保存到用户设备，后续优先使用本地文件，用户删除对应记录时一并清理。图片不进入 Git 仓库。数据不足或获取失败时保留名称和原有播放能力，不把无图当作播放失败。

建议功能名称为 **媒体资料与图片**，英文职责名为 `media-metadata`。这是一个业务能力的名称，并不意味着新建 Gradle 模块；数据、文件和 UI 仍分别归现有 model、base/support 和 app。功能包含来源解析、频道台标、影视海报/背景、匹配、保存、复用和删除。播放地址解析与解码仍由现有来源能力和 PlaybackSDK 负责。

此前阶段仅整理方案和只读验证公开接口。不得根据来源名称推断全部条目都是频道或影视：同一列表可以混合类型，文件扩展名也不能证明内容类别。

2026-11-27 更新：用户授权尝试代码、单元测试和指定设备运行；电影侧先提供本机凭据注入入口，无需用户在会话中提供密钥。当前已在 debug 源集实现试验性查询、文件读写及可选 WebP 转换，仍未接入页面、历史删除和产品级授权流程。

## 现有基线与边界

- [ImportedSource](../../model/src/debug/java/com/ai/playtv/model/bean/domain/source/ImportedSource.kt) 保存 `id`、名称、地址、播放格式，以及本轮新增的可选 `channelId` 和 `logoUrl`；仍没有影视类型、年份或资料库 ID。播放格式不能当作频道/影视类型。
- [SourceRules](../../model/src/debug/java/com/ai/playtv/model/repository/source/SourceRules.kt) 已从 M3U `#EXTINF` 读取名称、`tvg-id` 和 `tvg-logo`；台标地址解析为有效 HTTPS 地址后才保留，非法地址不会阻止播放项导入。TXT 来源未约定图片字段。
- [SourceHistoryStore](../../model/src/debug/java/com/ai/playtv/model/storage/source/SourceHistoryStore.kt) 将来源及候选列表以版本 1 的原子 JSON 保存于安装级 `noBackup` 目录；写入时保存非空的新增字段，读取时允许旧记录缺少这些字段。当前没有删除记录或图片管理入口；版本兼容和历史失败恢复仍需设备专项，不得把可选读取等同于迁移已完成验收。
- 现有入口及播放验证代码位于 debug 源集；正式页面、正式源集和设计宽度需由实际页面需求确认。公共 `network` 已启用；公共 `image` 尚未启用，不能假设 `ImageLoader` 已存在。若交付统一图片能力，须按项目公共能力与模板维护规则处理，并先说明新增依赖及影响。

## 数据来源与获取顺序

| 顺序 | 来源 | 用途与限制 |
|---|---|---|
| 1 | 用户导入的播放列表元数据 | 解析条目提供的名称、`tvg-id`、`tvg-logo` 等；有效图片地址优先。并非所有 M3U/TXT 都有这些字段，也不能把 `tvg-id` 当作一定正确的资料库 ID。 |
| 2 | [IPTV-org 数据接口](https://github.com/iptv-org/api) | 频道索引和台标索引可通过频道 ID 关联；适合候选台标，通常不能提供影视背景图。频道、别名及台标可能缺失、重复、失效或涉及不应展示的内容；图片地址和具体使用权需单独核对。 |
| 3 | [TMDB 搜索和图片接口](https://developer.themoviedb.org/docs/search-and-query-for-details) | 电影、电视剧候选及海报/背景图。需要申请 API Key；其 [FAQ](https://developer.themoviedb.org/docs/faq) 说明非商业免费用途须按要求署名，商业用途需另行授权。图片长期本地保存、发布方式与署名素材需按最终使用场景核实。 |
| 4 | [TVmaze API](https://www.tvmaze.com/api) | 电视剧/节目资料候选及部分海报、背景图；不是电影资料库。公开 API 无需 Key，官网说明 API 使用 CC BY-SA 并要求署名与遵守相同方式共享条款，接入前核实数据、图片及产品发布的具体适用性。 |

上述是候选数据源和建议顺序，并非已批准全部接入；不同来源的结果不能直接覆盖已确认匹配。公开索引只提供元数据或图片地址，索引本身可用不证明图片文件可访问、可保存或可用于产品。正式接入前核对来源条款、图片权利、访问稳定性、缓存期限与允许的用途；遵守项目受限第三方信息禁入规则，不能因数据来自公开接口而例外。

## 匹配规则

以下是目标规则；当前实现的范围和缺口见后面的“当前代码与接入边界”，不能将本节直接当作已有行为。

1. 按条目保留原名称和来源标识，生成独立的安全匹配输入；规范化仅用于比较，不改写用户显示名称，也不把用户输入直接作为文件路径。
2. 有可信的上游稳定 ID 时先匹配对应 ID；没有 ID 时才比较规范化后的名称与别名，并结合可获得的地区、语言和类型。相同名称的多个候选、冲突地区或类型均视为不确定，不自动选第一项。
3. 频道优先使用列表提供的有效台标，其次查频道索引。影视仅在类型与名称能够确定时查询电影/电视剧资料库；年份可用于消歧，不能凭空生成年份。列表缺少分类时保留未知，不把直播频道误判为影视剧。
4. 小图和背景图分别记录来源与状态：有小图但没有背景时保留小图；无可信结果、候选冲突、无图片或图片失效时显示原名称和页面既有无图状态。用户手动选择候选的交互和覆盖规则待页面需求确认。
5. 只在需要展示或用户触发刷新时按需获取；限制并发和频率，合并同一对象的重复请求。429、超时、网络断开、无结果与无权限分开处理，不能无限重试或阻塞播放。具体批量范围、刷新频率及匹配阈值待验证后确定。

## 数据契约与职责

建议由 model 的来源解析和媒体资料 Repository 处理来源元数据、候选匹配及持久化业务；图片加载入口只处理文件/图片显示和生命周期，不自行决定频道身份或删除业务。app 的页面和 ViewModel 按稳定记录 ID 请求与展示，不持有全局下载状态；SDK 不承担资料匹配。网络请求优先复用本项目已有 network 链路，具体 Service、DTO、Mapper 和组装路径在实施时按真实接口确定，不预设已有类。

领域数据至少需区分：所属来源 ID、条目稳定 ID、原始名称、已知类型/年份/频道 ID、匹配来源与可信度、各图片的本地文件引用及状态。外部链接、访问参数或凭据不能作为文件名、日志或公开缓存键；服务提供商密钥不能提交到仓库。旧版历史记录缺少新增字段时继续可读，迁移需明确版本与失败恢复，不能覆盖现有来源和候选列表。

### 后续接入顺序

1. 调用方先确定条目的真实类型、稳定来源 ID 和条目 ID；读取本地文件，缺失时再按需调用 `lookup`，对歧义、无结果和错误保留无图状态。不要把播放格式当成媒体类型。
2. 由功能作用域组装现有网络依赖、`ArtworkRepository` 和该目录唯一的 `ArtworkFileStore`；按产品确定的容量与 WebP 参数显式传入，调用 `ticket` 后用 `readImage` 的流调用 `save`。页面退出时取消其任务，网络所有者负责关闭资源。当前这些步骤仍需实现并验证。
3. 实现实际记录删除时，统一协调取消下载、历史提交和图片清理；先设计并验证失败/进程中断恢复及重新添加同一记录的边界。当前 `deleteItem` / `deleteSource` 的标记只覆盖文件操作开始之后的恢复，不能代替历史记录与文件之间的完整删除事务。
4. 先核实来源和图片的使用、署名及持久保存许可，再决定正式启用；电影凭据需要安全配置，不能写入仓库。接入前补齐并发合并、限频、实际页面展示与旧播放流程回归。

## 本地保存与删除

- 按用户要求，已成功保存的图片属于设备本地数据，而不是 Git 内容或仅依赖可能被系统清除的缓存。建议放在应用私有 `noBackupFilesDir` 下的受控功能目录，与当前历史记录的安装级、卸载清除、不参与系统备份语义一致；无需申请相册或广泛存储权限。图片来源如禁止持久保存或要求期限，以其条款为准，不能承诺无限期保存。
- 建议按来源 ID 和条目 ID 隔离图片，文件名使用内部安全标识及受控扩展名；不直接拼接名称或 URL。先下载到任务私有临时文件，限制大小、校验类型和解码结果，完成后再提交；失败或取消只清理该任务的临时文件。现有 `AppDirectories` / `AtomicFileStore` 的实际边界见 [公共基础](../rule/common-foundation.md)，不能假设它们已提供覆盖和关联删除。
- 初版建议每条记录拥有自己的文件副本，避免跨记录共用时误删；代价是相同图片可能重复占用空间。若以后引入共享去重，必须以引用关系或引用计数保护其他记录，最后一个引用移除后才删除文件。
- 删除来源时清理该来源下所有条目的图片；若页面支持单独删除条目，只清理该条目拥有的图片。先使对应请求代次失效并取消任务，再协调记录与文件删除；迟到下载不能重新写回已删除的记录。文件删除失败、进程中断或部分成功要保留可恢复的清理记录并重试或提示，不能静默报告已全部清除。
- 设置可配置的单图、总容量和并发上限；数值待设备与业务验证。空间不足时停止新增并保留已有记录，不自动删除用户已保存的图片。用户清缓存与删除记录是不同动作；已保存图片不能因普通清缓存丢失。Android 卸载会清除应用私有目录。

### WebP 转换试验

- 用户希望缩小本地图片体积。debug 实现支持为保存动作显式传入 `AndroidWebpEncoder`：按调用方传入的目标尺寸缩小静态 JPEG/PNG，背景使用可配置的 WebP 有损质量；小图在 Android 11 及以上使用无损 WebP，保留透明度。Android 8–10 走系统旧 WebP 编码，透明度和效果须分别验证。
- 本次设备试验使用小图最长边 512 px、背景最大 1920×1080 px、背景质量 80；这是测试参数，不是已经确认的产品配置。转换后不比原文件小时保留原文件；已有 WebP、GIF、动画 PNG 和带旋转方向的 JPEG 暂保留原图，避免丢动画或改变方向。失败不会覆盖此前已保存的图片。
- 图片文件以内部 ID 及用途命名，实际类型应按文件内容识别；当前试验文件后缀不是产品对外格式契约。编码实现尚未接入页面和自动保存入口，也不能把这次两张样本的压缩率推广到所有图片。

## 页面、状态与生命周期

不新增独立页面或预设视觉资产；由现有或后续页面按其 Spec 展示小图、背景和已有无图样式。图片可分别处于未请求、获取中、本地可用、无匹配、失败或待清理状态；普通图片失败只影响局部，不弹全屏 Loading，不阻断来源解析与播放。候选选择、刷新、删除确认的实际入口和中英文文案需随具体页面确认。

同一条目的重复请求应合并或替换；绑定新条目或空图片时取消旧目标并清除旧图，避免列表复用显示错图。任务作用域、页面退出后的继续/取消策略、进程重建恢复由实施方案明确；无跨重启持久任务需求时不新增 Service 或通知。日志只记录非敏感标识和错误类别，不输出带参数的来源链接、密钥或图片内容。
