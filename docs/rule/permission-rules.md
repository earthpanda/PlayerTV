# PlayTV 权限、系统授权与能力准入

本文件负责本项目权限申请、拒绝、设置页和宿主生命周期；文件访问方式见 [存储规则](file-storage-rules.md)。本项目实际权限场景与已接入能力见 [项目基线](project-context.md)、Manifest 和 [组件目录](ui-component-catalog.md)，不能因为有本规则就假定已接入权限 SDK。

## 先问功能需要什么能力

- 在用户触发对应动作时申请最小必要集合。进入明确的功能页可按 Spec 自动申请一次；普通启动不批量索要所有权限。录音、扫描、通知、定位各自按真实功能拆分。
- Spec 记录能力、Manifest 声明、运行版本/targetSdk 条件、申请入口、授权充分条件、拒绝降级、回到设置后的行为。不能照抄其他项目的一组 BLE/存储权限。
- 先检查是否能用不要求广泛权限的系统接口：应用私有文件通常无需存储权限；选择单张图片优先照片选择器；选择文档优先 SAF。
- 运行时权限、特殊访问权限、系统服务开关、登录/会员等业务资格分开建模。蓝牙权限已获准不代表蓝牙开启，定位获准不代表位置服务可用。

| 能力 | 必须核对的系统差异，不能当作完整权限清单 |
|---|---|
| 麦克风、直接相机访问 | 本项目初始化 minSdk 26 已处于运行时权限范围；后续以 app Gradle 为准，不能 Android 12 以下直接视为授权 |
| 通知 | POST_NOTIFICATIONS 的运行时门槛是 Android 13/API 33；还需检查通知总开关/渠道，不能以 API 31 代替 |
| 蓝牙扫描/连接 | Android 12+ 附近设备权限与旧系统定位要求不同；定位用途、neverForLocation 等按实际行为核对 |
| 图片/音频/视频读取 | 系统版本、照片选择器、选中照片访问及媒体类型不同；不是一个 READ_STORAGE 永久通用 |
| 定位 | 精确/大致、前台/后台分开，用户仅授予大致定位能否继续由功能定义 |
| 悬浮窗等特殊访问 | 使用对应系统设置入口与查询 API，不当作普通运行时权限申请 |

以上仅是易错点。新增能力时按当前 compile/targetSdk 和 Android 官方文档确认 Manifest、系统限制及后台要求，再写入项目自己的能力说明。

## 分层与返回结果

- 权限状态查询可由无业务的平台能力完成；系统弹窗/Activity Result 由 app 的 Activity/Fragment 或短寿命控制器承载。第三方权限库的适配放 support。
- model 表达“开始动作前需要何种业务能力”及后续动作，不持有 Activity、不直接弹授权说明、不调用 app 的 R。页面通过 Effect/宿主协作完成申请后，回传语义结果。
- 不能只用一个 Boolean 混合所有情况。按需求区分：已满足、用户拒绝、可提供说明、可能需设置处理、部分满足、取消/宿主失效、系统能力不可用。
- `shouldShowRequestPermissionRationale == false` 也可能是首次申请或系统策略，不足以单独判断永久拒绝。结合是否曾请求、实际结果与平台行为解释；不作绝对承诺。
- 缓存“请求过”仅用于交互判断，不能作为授权事实。每次真正使用前重新查询，调用系统 API 时仍处理撤销权限和 SecurityException。

## 申请与生命周期

1. UI 确认用户意图和当前宿主有效，查询最小必需权限及系统开关。
2. 普通运行时权限默认直接请求系统弹框，不要求用户先点单独的“申请权限”按钮，不默认先弹自定义说明。SDK/平台确有额外用途说明要求时按该能力处理。系统弹窗由当前页面统一调度。
3. 通过生命周期内稳定注册的 Activity Result launcher 或已确认封装申请。注册顺序稳定，不能在点击时临时注册；禁止从全局单例保存 launcher/Activity。
4. 结果按项判断是否足以执行动作，重新检查状态；授权后最多恢复一次仍有效的原操作。若页面已离开、账号已切换或用户已取消，不自动执行旧操作。
5. 拒绝后 Toast 说明对当前功能的影响，结束本次操作并保留无关功能。功能入口仍可点击，下次触发重新检查并尝试请求；不能因为拒绝权限永久禁用入口。系统不再提供弹框时建议用户确认进入设置，不循环弹窗或自动跳设置。
6. 从设置回来重新查询，不能把“打开过设置页”或“关闭应用说明弹窗”当授权成功。默认只刷新能力，用户再次触发功能；不在 onResume 自动重放旧录音/上传/Service 启动。

- 同一宿主由一个控制器串行调度；已有系统请求时可明确返回 Busy，调用方决定忽略、合并或排队，不能覆盖正在等待的 continuation/callback。每个请求有明确所有者；取消原动作后，旧系统结果返回前不能启动新请求。
- 回调转 suspend 时正确处理取消、宿主销毁、重复/迟到回调和至多一次完成；协程取消不一定能关闭系统弹窗，但回调不得恢复已取消动作。
- 权限状态变化可能触发进程重建；只保留可恢复的小型动作标识，不能持久化 Activity/回调，更不能重建后无条件重放有副作用操作。
- 没有 Activity 可接收系统结果、无权限或 API 不支持时返回明确结果，不用 applicationContext 强行伪造可用宿主。

## 多权限 List 与模板交付

- 必需权限 List 按同一次功能意图处理，先复查全部，再申请；全部通过才继续。部分授权不等于成功，不能仅检查 grantedList 非空。拒绝 Toast 可按实际缺失项列出能力，再次点击重新查询并尝试申请。
- 当前版本无需的权限先排除；保留平台要求同时申请的组合，需分步的权限按平台顺序分开。List 不承诺系统只弹一个框。可选权限与必需组分开，支持部分授权降级则按 Spec 逐项判断。
- 模板的 `permissions` 为选填能力，启用后交付 `PermissionActionController`、底层 `PermissionController/PermissionResult`、中英文提示及 `PermissionUsageExample`。高层接受 List/Set、默认全部必需，拒绝统一 Toast 并建议设置；底层保留逐项结果供差异化降级。同一宿主二者择一创建，高层内部已有底层控制器。
- 应用自己的设置引导框称为 `CustomSettingsRedirectDialog`，不把它称为系统权限申请框。默认样式及 `SettingsRedirectDialogFactory` 随 permissions 交付；项目按数据契约放置定制 Dialog，通过工厂注入，不复制权限流程。控制器负责展示、关闭、确认去重及旧弹窗回调失效；工厂不全局持有宿主、不自己 show、不覆盖关闭监听。系统授权弹框本身不能自定义。
- 控制器 onCreate 稳定注册，STARTED 后从功能入口调用。进入页自动申请只允许一次并保存标记，不在 render/onResume 无条件申请；onStop 使旧业务动作失效，系统请求返回前不释放占位，设置返回只复查。
- 业务接入先读组件目录确认该能力已启用，再读生成的 `docs/template-capabilities/permissions.md` 与 debug 的 `permission/example/PermissionUsageExample.kt`；包含单项、List、部分拒绝文案、生命周期和设置处理代码。未启用时不能只凭规则猜测 API 已存在。

权限文案进入 strings.xml 并说明具体用途。具体所需权限、Toast 内容、设置目标和降级由功能 Spec/UI 定义；公共封装只执行选定交互，不继承参考项目的业务权限组合。规范从模板生成；模板更新后已有业务工程逐项采用适用变化，不重跑初始化器覆盖业务实现。
