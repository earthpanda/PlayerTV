# PlayTV Manager、依赖组装与生命周期

本文件负责本项目 Manager/服务的职责、作用域、初始化、并发和释放；模块归属以 [数据契约](data-contract-rules.md) 为准。名称示例仅描述角色，实际能力与适用边界见 [组件目录](ui-component-catalog.md) 和 [项目基线](project-context.md)，不能据此推定已有同名 Manager。

## 先判断是否需要 Manager

先按 [数据契约的角色判定](data-contract-rules.md#业务角色的唯一判定) 确认是否确有持续资源/会话/队列调度职责；普通计算、一次业务动作和数据读写不因复杂就命名 Manager。本文件只规定选定该角色后的所有权与生命周期，不再维护另一份角色表。

不要为了“统一入口”再增加一个汇集所有业务的超级 Manager。`Manager` 后缀不等于单例，也不意味着应该在 Application 中启动。

## 固定初始化与依赖入口

- `AppApplication.onCreate` 先经 StartupStep 初始化 Foundation，再构造并发布 `AppContainer`。启用 MMKV 时由容器初始化引擎；打开文件/恢复功能数据在 IO 或对应功能启动时执行，不在 Application 扫描文件、自动请求接口。
- `StartupStep` 逐项记录耗时/失败类型；必需初始化失败重抛，不能 catch 后发布半初始化容器。日志默认 WARN/ERROR，查看成功耗时须显式启用 INFO。可选能力按功能定义可降级状态，不能把全部 init 包进一个 catch。
- AppContainer 用明确命名的属性持有应用依赖；Factory 为 ViewModelStore 构造 ViewModel。禁止容器直接缓存 ViewModel、通过单例跨页复用它，禁止 get(Class)/字符串服务定位器。
- `NetworkDependencies` 一后端/作用域一份，集中客户端、解析器、RequestExecutor 和 Service 构造；功能子容器持有 Repository/Store。真实地址由 app/config 传入，不为满足初始化创建虚构生产 URL。
- 页面独占的子容器由 ViewModel 持有并在 onCleared 关闭；共享网络/会话资源由上级所有者关闭，页面只取消自己的任务。旋转不关闭 ViewModel；不能依赖 Application.onTerminate，它在真实设备上不保证调用。
- 初始化存在并发时一次成功后才发布，失败可重试不残留半成品。资源构造中途失败立即关闭此前创建资源；close 幂等，结束后拒绝新动作。系统权限请求仍由有生命周期的 UI 宿主执行。

## 一个 Manager 必须交代的契约

- **职责**：管理哪一种资源/流程，什么明确由调用方负责；名字对应职责，避免 CommonManager/AllManager。
- **所有者和作用域**：进程、账号会话、单任务或页面；由谁创建、持有、关闭。作用域越短越不应被长寿命对象持有。
- **依赖**：构造参数显式传入所需接口、调度器和作用域快照；在 app 组合根组装、通过 ViewModel Factory 等传入。默认手动组装即可，不自动引入 DI 框架。
- **线程与并发**：公开方法在哪个线程调用、是否挂起、是否可重入、重复调用如何处理；共享可变状态采用串行执行、Mutex 或其他明确方案。
- **初始化**：是否懒初始化、先决依赖、是否有 SDK 要求的主线程调用；初始化中/成功/失败可观察，失败能否重试、已创建资源如何回收。
- **结束**：close/dispose/release 的职责、是否幂等、结束后能否再用。清 Job、监听器、回调、连接和缓存引用；不能靠 Activity finish 或进程退出“顺带释放”。
- **错误**：按动作返回有意义的结果或失败；不可把所有异常吞掉后仍标记已初始化。取消、日志与业务失败按 [业务规则](business-development-rules.md) 处理。

## 生命周期与状态

- 无可变会话状态、资源可安全共用的能力才考虑 `object`。账号状态/连接/队列优先每会话实例；多任务状态优先每任务实例，避免一套全局字段互相覆盖。
- 长寿命能力仅持有必要的 applicationContext，不持有 Activity、Fragment、Binding 或弹窗。需要当前宿主的动作由短寿命 UI 控制器执行。
- Scope 绑定真实所有者：页面任务跟随 ViewModel/视图，会话任务跟随登录会话；确需进程级 Scope 时由组合根持有并提供清理入口，不散落 GlobalScope。
- 对外暴露只读 StateFlow/Flow 和语义操作，内部状态私有；状态更新原子化。订阅方生命周期与重放策略写清楚，不把短暂事件永久当状态重放。
- 初始化保证并发只执行一次；失败后不留下半成品 singleton。若 SDK 必须预初始化，仅把最小必要部分放启动路径，其他能力按需启动。
- 有初始化依赖时写出顺序和失败影响；一个大 try/catch 包住全部初始化会让后续能力悄悄缺失，应逐项定义必需/可降级及可观测结果。

Android Service 的共享连接、任务所有权、前台状态与系统通知另按 [Service 与通知](android-service-notification-rules.md)；本文件的初始化/释放约定仍适用。不能把业务 Manager 存在理解为必须启动 Android Service。

## 会话、环境与后台任务

切换账号/环境是一条受控流程：停止接收旧操作 → 使旧任务代次失效 → 取消/等待或隔离旧任务 → 释放连接/数据库等旧依赖 → 切换存储与依赖 → 发布新状态。异步完成时使用启动任务时捕获的作用域，不能临时读取“当前用户”后落盘。

不要长期缓存会因环境变更而失效的 Retrofit service/数据库实例；选择重建所属实例或受控动态提供，并说明所有调用方何时切换。退出登录、清用户数据、注销账号是不同动作，清理范围见存储规则。

需要跨页面继续的工作不能由某个页面的 ViewModel 偶然持有；需要跨进程重启继续的工作不能只靠内存 Manager。按需求选择持久任务调度、前台服务等 Android 能力，并单独声明系统限制和依赖，不预先为所有项目安装。

审阅时能回答：谁创建、谁关闭、重复 init/close 怎样、初始化失败怎样、并发操作怎样、切用户后旧回调怎样。不能只写一个 `init(context)` 就认为封装完成。
