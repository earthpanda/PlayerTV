# PlayTV 公共 Loading、Toast 与 Dialog

本文件负责公共反馈的场景选择、构建和交互契约。类命名只在 [项目约定](project-conventions.md) 维护，目录归属只在 [数据契约](data-contract-rules.md) 维护，真实可用入口与常用说法只在 [组件目录](ui-component-catalog.md) 登记。本文中的候选角色不是已交付 API。

已有页面状态、系统 Toast 和可选设置引导的实际 API 用法见 [接入与登记示例](../reference/ui-feedback/README.md)。

## 从用户的描述找到入口

收到“加载一下、用公共提示、弹个确认框”等描述时，先查组件目录的“按使用场景查找”，读取命中项的源码和调用示例，再决定复用或补齐。场景 ID 是文档检索键，不是运行时服务定位器、反射注册表或 model 枚举。

普通描述不足以区分场景时，先结合动作和现有 Spec：首次读取用页面状态，刷新用列表刷新状态，提交用操作状态。只有仍影响行为的决定缺失时才询问，例如是否阻塞、能否取消；用户无需记住组件类名。缺少组件时按已有需求补实现并登记，不悄悄用另一个语义代替。

## Loading 按任务范围选择

| 场景 | 表达方式 | 收尾与并发 |
|---|---|---|
| 首屏加载 | 页面 State 表达初始/加载/内容/空/失败，UI 渲染页面状态组件 | 页面已有内容时按业务保留；不因刷新改成整屏空白 |
| 列表刷新/分页 | 刷新和分页各自的 State，已启用容器负责对应动画 | 手势被拒绝、失败、取消和跳过中间 State 都要结束实际动画 |
| 保存/提交等操作 | State 表达本动作 busy；局部加载或操作遮罩由 Spec 决定 | 禁止重复提交由动作层保证；不能把一个全局 Boolean 当多个任务的真源 |
| 按钮/卡片局部加载 | 只影响所属区域的 State 和可操作性 | 不能阻止无关区域；按钮形态沿用项目约定 |

持续 Loading 由最新 State 渲染，不用一次性 ShowLoading/HideLoading Effect 配对维持事实。渲染必须幂等；旋转重建后从最新 State 恢复，不再次启动任务。多个动作共享同一遮罩时，按稳定 actionId/操作租约协调，旧任务的结束不能关闭新任务的展示。只有出现真实并发需求时才增加该机制。

项目页面的加载展示统一使用组件目录登记的 `CustomLoadingView` 外观；操作遮罩通过项目工厂创建已有 `OperationLoadingController`，保留各场景原有的阻塞和取消语义。页面状态与局部加载按各自范围使用同一外观，不为统一视觉改变业务状态或遮罩范围。

加载期间保留原页面内容、焦点和选中状态；已有内容不因显示 Loading 被清空、重排或重置，加载展示不使原页面变暗。加载完成后按任务结果正常更新页面，取消与返回仍按各场景契约处理。

遮罩是否阻塞触摸、允许返回或点外部关闭由 Spec 决定。关闭展示与取消任务是不同操作；允许取消时回传意图，由任务所有者取消，UI 再按 State 收尾，不能只隐藏遮罩却默认任务已结束。失败或取消都要复位 busy，错误提示由动作结果决定。

## Toast 与短暂消息

成功、失败、警告和普通提示是展示语义，最终文字和资源由 UI 解析。业务层返回类型化结果/Effect，不引用 Toast、Activity 或项目 R。短暂消息不代替需要用户处理的页面错误、字段错误或确认弹窗。

有公共消息入口时所有同场景调用通过该入口；默认采用现有平台能力，不为统一名字引入第三方 SDK。项目需要自定义浮层时，通过实例渲染器或 View 工厂替换展示，沿用同一消息入口和语义，不另建一套业务通知管线。

明确消息所属宿主、时长、重复消息和快速连续消息的替换/排队策略。有队列时必须有容量和过期策略。离开页面后是否仍展示按场景定义；页面反馈默认不转投其他 Activity，不使用 getTopActivity 或进程单例保存页面 View。自定义消息 View 不等于 Android 系统 Toast，自定义展示的窗口/宿主限制要如实登记。

feedback 是公共反馈的选填实现，是否启用查组件目录。其演练通过 MessageController 统一入口；模板基础样例和 permissions 内部仍有历史系统 Toast，不代表已全量迁移。后续迁移逐项登记实际调用范围。

## Dialog 的职责与结果

确认、设置引导、底部操作面板是不同用途，分别登记。确认弹窗只展示输入与回传 Confirm/Cancel；遮罩、返回和关闭是否算取消需明确。业务删除、网络请求和系统设置跳转由宿主/动作所有者执行，不藏在公共 Dialog 内。

工厂只创建实例；控制器/宿主负责 show、dismiss、去重和清理。状态驱动弹窗用稳定 actionId 判断当前操作，旧实例迟到的确认不能执行新操作。普通重绘不能重复创建或排队，关闭监听不能被多个所有者互相覆盖。

Dialog 生命周期、Fragment view 生命周期及状态恢复统一遵循 [UI 生命周期](android-ui-lifecycle-rules.md)。普通 Dialog 关闭后是否允许重复使用必须写明；不复制自建 LifecycleRegistry/ViewModelStore 的历史实现。需要配置变化恢复时按实际承载方式设计，不能重复执行确认后的业务动作。

## 构建方式与样式替换

按职责组合，不要求每个组件都创建三层：

1. **任务/页面事实**：在现有 model State/Effect 表达 busy、结果和意图；不携带 Dialog、View、Context、回调或文案资源。
2. **宿主展示协调**：确需持有窗口、延迟或多任务时才建 Controller，由 Activity 或 Fragment 的 view 宿主持有。主线程操作，明确停止/销毁策略和幂等 close；全局容器不持有页面控制器。
3. **视觉实现**：Custom…View/Dialog 只负责渲染和回传操作。不同功能共享同一默认实现；业务定制通过参数、style 或实际需要的 Factory/Renderer 注入。仅换颜色/文字时不必额外造接口。

普通页面状态可以直接 render，不额外包 Controller。多个功能共用确认框不代表必须建立统一管理所有 Toast/Loading/Dialog 的万能 Manager。跨页面消息排队属于独立需求。

项目样式由 app 提供，无业务默认组件可以归 base；没有第三方 SDK 的展示能力不放 support。项目设计资产遵循原有提供规则，不从参考工程复制图标和动效。不要求所有项目启用公共操作 Loading 或自定义 Toast。

## 新增或替换公共组件的交付顺序

1. 按场景检索现有实现，判断复用、参数扩展、style/include，还是新增有独立状态/交互的组件。
2. 明确用途、状态、宿主、输入/结果、主线程契约、取消、重复操作及样式扩展；按项目约定命名、数据契约定位文件。
3. 有真实源码、必要资源和调用示例后，更新组件目录中的场景目标和条目；常用说法、默认入口、配置、生命周期、真实路径、验证状态一起登记。
4. 替换旧入口时核对真实调用，登记仍未迁移的调用位置及范围；不能只改目录让 AI 误以为全部统一。业务专用弹窗可以继续保留，只有同一语义的公共入口需要统一。
5. 模板维护先提供可独立使用的实现/示例/Markdown；选填运行源码以完整 capability 交付，未选不初始化。仅提供组织说明时明确“规范/待实现”，不能登记为已注册包。

无真实需求不预建空类或新增 SDK。feedback 可按需交付公共操作 Loading、消息与确认组件，实际是否生成和采用仍统一查组件目录，不凭规范名称假定启用。
