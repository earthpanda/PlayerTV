# 数据库、同步、整合与后处理

本文件统一数据库到 UI 的执行规则。存储位置/备份/清理仍见 [存储规则](file-storage-rules.md)，模块归属见 [数据契约](data-contract-rules.md)，网络入口见 [网络请求](network-request-rules.md)。规则不等于所有项目默认启用云同步；以组件目录、依赖与具体 Spec 为准。

## 固定链路与线程

```text
网络/文件/设备输入 → 协议校验 → Default 整理/去重 → IO 事务合并
                                          ├─ 数据 + 冲突 + 游标 + 后处理任务
                                          └─ 提交 → Room Flow → ViewModel State → Main UI
后处理任务 → Default 计算 → IO 事务校验输入版本后提交 → 同一观察链路
本地编辑 → IO 事务写内容 + outbox → 后台上传 → 版本校验确认 → 同一观察链路
```

- RoomDatabaseFactory 是技术构建入口，明确禁止主线程创建/查询；库在 IO 首次创建。启用本模板 kapt + Room 2.4.1 时，DAO 单次操作使用普通 fun，Store 对外保留 suspend，并用 withContext(IO) 执行阻塞 DAO；持续展示用 Flow。多语句事务统一用 RoomTransactions.withIoTransaction，事务块不挂起，在同一 IO 线程执行 SQL，提交前检查取消；异常回滚，提交后取消不撤销已提交数据。不能将同步 DAO 混入可挂起事务块，也不能因 DAO 改成普通方法就在 Main 直接调用。清洗/排序/聚合/大映射用 Default。
- 不为了“同步展示”打开 allowMainThreadQueries。同步展示的含义是事务提交后可观察，不能是堵住 UI 等数据库。ViewModel 在 Main 更新 State；页面用 repeatOnLifecycle 收集；停止收集不等于停止应用级同步。
- 页面不直接访问 DAO，不在网络回调手工修改另一份列表，不用 EventBus/固定延时来保证刷新。Repository 暴露数据库来源的不可变快照，失败保留上次成功内容；初始化中、空库、读取失败分别表达。
- 列表+总数、主表+子表等必须一致的多次读取，在同一只读事务构成快照后发射；不能用两个独立 Flow 的 combine 就声称事务一致。可用 InvalidationTracker.observeInvalidations 触发事务重读，并用 distinctUntilChanged 避免无效渲染。每条 invalidation 只表示“需重读”，不是业务事件队列。
- 查询只投影 UI 需要的字段，分页/批次有上限；DiffUtil/ListAdapter 更新。不能在 render 中查库、排序全量数据或逐项请求关联表。表关系优先 JOIN/@Relation 事务，索引依据真实查询；无限列表用稳定游标或按需求引入 Paging。

## 目录和数据库所有权

| 角色 | 位置 | 约束 |
|---|---|---|
| DatabaseScope / RoomDatabaseFactory / PagedSyncRunner | support/database | 固定所有者/环境，技术线程、取消和事务接入契约；不知道业务账号/表/成功码 |
| Entity / 持久任务 | model/bean/local/&lt;feature&gt; | 稳定主键/协议字段，内容版本与本地编辑版本分开 |
| Database / Migration | model/database/&lt;database&gt; | 实际 schema、完整迁移；共享库按数据库归属组织 |
| DAO | model/database/dao/&lt;feature&gt; | SQL、投影和条件更新，无网络/UI |
| Store | model/storage/&lt;feature&gt; | IO/事务、合并、冲突、版本与持久任务 |
| Repository / 必需的 SyncCoordinator | model/repository/&lt;feature&gt; 或 manager/&lt;feature&gt; | 输入源、上传/拉取顺序、重试和会话执行；普通 CRUD 不强建 Manager |
| Dependencies / 系统 Worker | app/di、app 对应功能后台目录 | 构造固定作用域依赖；平台触发、取消与资源释放 |

应用/会话子容器拥有数据库，每个数据库作用域一个实例；页面不关闭共享库。切号先取消并等待旧任务结束、解绑观察，再关闭该作用域，禁止旧结果写入新账号。SINGLE_PROCESS/进程内 Mutex 不是跨进程锁；跨进程需另行设计数据库条件更新和调度。

数据库默认无 destructive fallback、无主线程查询、schema 导出开启。schema JSON 由实际 Room 编译生成并纳入版本管理，不能手造 identityHash。升级必须有从所有已发布版本到新版本的连续迁移和数据验证；缺迁移报可诊断错误，不能自动删库。降级、损坏恢复、备份排除和导出由 Spec 明确。

## 输入、合并和提交

1. Spec 先确定真源、全量/增量协议、稳定 ID、远端 revision/ETag、删除标记、游标语义、分页上限、本地可编辑字段及冲突决策。不可用本机时间戳推断服务端更新顺序，不发明后台没有的版本号或幂等能力。
2. 先在事务外获取/校验输入，Default 整理并以稳定 ID 去重。同一版本不同内容按协议错误处理，不能凭响应顺序覆盖。解析错误不伪装空列表；请求尚未成功不清空本地。
3. 短事务读取当前值、按实际协议比较版本、定向更新相关列，写入冲突记录和后处理任务，最后更新游标。数据、冲突、任务和该页游标必须同事务。事务内不请求接口、不写大文件、不做重计算、不等待用户。
4. 旧版本跳过，重放幂等；本地 dirty 与远端更新冲突时保留本地及远端影子并显式解决，默认不静默 last-write-wins。服务端不拥有的本地展示偏好不能被 DTO 全对象替换覆盖。
5. 分页逐页提交意味着 UI 可以看到部分已同步结果，State 同时展示同步进度；后页失败保留已提交页并从其游标恢复。若产品要求整个快照一起发布，使用 staging 表/generation，完整验证后事务切换 active generation；不能边清旧库边导入。
6. 全量快照确认范围和完成后才识别缺失项；增量响应里“没出现”不等于已删除。删除使用协议 tombstone，结合远端确认和保留期清理，避免旧页把已删数据复活。

## 同步后处理

- 单纯、廉价且必须一致的派生字段可以随事务写入。耗时清洗、索引、摘要、统计、文件解码另建持久处理任务，与原始数据同事务入库；不能提交后只 launch 一次协程就认为可恢复。
- 任务绑定固定作用域、实体 ID 和输入内容版本/token，Default 计算后在事务用条件更新提交；输入已变化时丢弃旧计算结果，只清本任务，不删除更新的任务。派生结果不能覆盖新原始数据。
- UI 明确“原始数据已就绪/处理中/处理失败/结果就绪”，派生结果未完成时不能显示上一版结果为当前结果。失败保留任务与诊断信息，按错误类型有限重试；进程重启/重新进入时恢复，正式后台需求由唯一 Worker 调度。
- 跨记录聚合使用 generation/版本水位，提交时再核对依赖；大文件产物采用临时文件→完成文件→数据库索引和孤儿核对，不宣称文件+库同事务。

## 本地编辑、outbox 与上传确认

- 本地内容更新、localVersion 增长、dirty/删除标记和 outbox 在同一事务写入。operationId 是稳定重试幂等键，后续重试不得每次生成新键；本地新编辑生成新的操作版本。
- 上传读取不可变任务快照，网络在事务外；服务端需按约定支持幂等键和条件版本。确认后只清已发送的 operationId/localVersion。期间又编辑时保留新内容/新任务，在协议允许时更新新任务的 baseRevision，不能把整行直接标已同步。
- 服务端拒绝基础版本或发现其他远端变化时先落冲突/重新拉取，不能自动强传覆盖。已发送任务崩溃重试靠服务端幂等返回原确认；本地事务无法保证远端请求恰好一次。
- 离线/临时网络错误可有限指数退避；鉴权失败暂停所属会话并按既有规则处理；协议/校验/冲突错误不能无限重试。达到上限保留任务及用户可见失败。任务需要 attempt/nextAttemptAt/lastError 等字段时随真实需求实现，不虚称样例已包含生产队列。

## 并发、取消、恢复与诊断

- 同一作用域/同步流共用一个 Coordinator，手动刷新、启动、Worker、SSE 触发先合并/拒绝重复，不并行全量拉取。PagedSyncRunner 同实例重复调用返回 Busy；事务还必须校验 expectedCursor，防止不同实例/迟到页提交。
- SSE 推送按协议视为增量输入或触发重新拉取，同样经过校验与事务，不直接改 UI。游标必须前进，防游标循环；页大小、总页数、内存和并发有上限，不能无界 async。
- CancellationException 必须重抛。取消前已经提交的页/任务不会回滚；下次从持久游标和任务恢复，不返回假空列表。数据库提交与 UI 成功回执之间取消时允许重读确认。
- 正式后台用固定作用域唯一 WorkManager 工作，声明网络等实际约束、重试类别/上限和停止行为；Worker 不负责准点响铃。数据库与外部系统不是同一个事务，用持久意图+幂等执行+恢复核对，不承诺恰好一次。
- 日志记录阶段、耗时、批次、应用/忽略/冲突数量、错误类别、重试次数与脱敏关联 ID。禁止正文、令牌、用户原始标识和完整游标；失败必须可追踪，不只返回 false。

## 当前实现与验证边界

本项目未启用 room；以下是数据库与同步的开发标准，不代表已经接入 SDK、数据库或同步器。需要时先补齐真实依赖、源码与调用示例，再登记组件目录。

人工验收至少包含：提交后刷新、空/失败区别、重复/乱序页、游标不前进、第二页失败、重启恢复、本地编辑同时拉取/上传、确认时再次编辑、旧计算完成、删除重放、作用域切换、迁移失败和磁盘满。当前仅源码/配置与静态核对，Android 构建、schema 生成和运行均待用户明确授权。
